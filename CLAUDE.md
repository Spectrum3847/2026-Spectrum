## Architecture — read this before writing any subsystem code

Every mechanism is a **two-enum state machine**, not a command factory. The
pattern is identical in all eight subsystems, so learning it once from
`hood/Hood.java` (232 lines, the cheapest example) covers the rest:

```java
public enum WantedState { ... }     // what callers ask for
public enum SystemState { ... }     // what the mechanism is actually doing
public void setWantedState(WantedState s)   // the only public entry point
private SystemState handleStateTransition() // Wanted -> System, usually 1:1
private void applyStates()                  // System -> motor output, called from periodic()
```

`subsystems/SuperStructure.java` is the coordinator. It owns
`WantedSuperState` / `CurrentSuperState` and drives every mechanism's
`setWantedState(...)` from its own `periodic()`. **Subsystems never call each
other.** If two mechanisms need to agree, the logic goes in `SuperStructure`.

`Robot.java` constructs everything, holds all subsystems as `@Getter private
static`, and owns `Robot.Config` — the aggregate of every subsystem config.
Per-robot configs in `configs/` extend `Robot.Config` and set encoder offsets
plus `setAttached(...)` flags. Selection is `switch (Rio.id)` in the `Robot`
constructor; today that switch has only a `default` arm returning `OM2026`.

Gamepad bindings live in `pilot/Pilot.java` and `operator/Operator.java` as
`public final Trigger` fields composed from `Gamepad` base triggers
(`LB.and(selectButton)`, `AButton.and(disabled)`, …). They are wired to
commands in `Robot.configureBindings()`.

Mechanisms extend `spectrumLib/mechanism/Mechanism.java`, which wraps TalonFX
config and control modes and does one Phoenix `refreshAll` per loop keyed on
`RobotLoop`, so every getter in a loop sees the same sample.

## Conventions

- Lombok `@Getter` on fields instead of hand-written getters — a getter you
  cannot grep for is probably generated. Search the field name too.
- Config values are `@Getter private final double` inside the subsystem's
  `*Config` class, applied through `config*()` helpers in the `Config`
  constructor.
- Commands bound to triggers get wrapped in `Telemetry.log(...)` so the
  lifecycle lands in the wpilog.
- Non-obvious constants carry a comment naming the bench date and the symptom
  that produced them (see `Hood.homeRestToleranceDegrees`). Keep that habit —
  it is the reason those numbers are auditable.
- SpotBugs exclusions: `excludeFilter-spotbugs.xml`. ErrorProne is on.

## Docs

`docs/` is ~4000 lines aimed at humans, split into a beginners' curriculum and
a reference (`docs/index.md`). Start from `docs/other-guides/2026-season-specific.md`
for architecture and `docs/tools/` for a specific tool.

Where docs and code disagree, the code wins — and say so, rather than working
around it. Docs drift is what makes this repo expensive to work in: as of
2026-09 a sweep removed ~90 references to a 2025 `RobotStates` / `Coordinator`
/ `*States` architecture that no longer exists, plus 25 dead source links. If
you change how something is structured, grep `docs/` for the old name in the
same commit.

This file is the single source of agent guidance.
`.github/copilot-instructions.md` points here rather than keeping its own copy;
keep it that way.
